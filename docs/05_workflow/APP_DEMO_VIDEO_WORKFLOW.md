# App 介绍视频制作工作流

T-394，2026-09-15。适用于真实 App 界面驱动的介绍片、发布会式演示和功能短片；以 T-393 的实际返工及用户反馈为依据。本文是后续制作的按需入口，不是自动执行授权，也不表示已经重做视频。

**核心顺序：先证明视觉表达，再扩展制作；先复用素材，再补拍缺口；技术、视觉、真实性和数据恢复分别验收。**

本文定义视频制作方法，不复制账号、安全或任务管理规则。[Development Guide](DEVELOPMENT_GUIDE.md)仍拥有这些边界；需要改 App 或后端才能拍摄时，先判断是否属于已采用目标，不把产品开发悄悄塞进剪辑任务。

## 1. 两分钟启动

1. 读本页速查和对应阶段，不先扫描整个仓库或重读全部历史对话。
2. 查看 Git 状态、[Current State](../00_memory/CURRENT_STATE.md)和现有视频工程 README；保留其他任务的文件、设备、账号与工具占用。
3. 在一份制作记录中写明片长、受众、一句核心信息、画幅、语言、声音、真实性、交付位置及既有授权。已明确的信息不再询问。
4. 清点旧素材，标为可用、需核对、缺失；审美返工默认不重新登录、不重新造数据、不重新走业务全流程。
5. 选定视觉参考与最难的 12-15 秒连续段，先证明镜头变化、转场、阅读停留与信息推进成立。
6. 样片通过后才批量补拍和扩展全片。任何不可逆业务操作前，必须已有精确恢复方案。

### 阶段门槛

| 阶段 | 最小输出 | 继续条件 | 不通过时只回到 |
|---|---|---|---|
| A 范围与复用 | 制作简报、素材缺口表 | 交付与授权边界明确 | 缺失的范围或资料 |
| B 脚本与动效样片 | 镜头表、12-15 秒连续样片 | 信息、视觉、技术三项分别有结论 | 文案、构图或镜头设计 |
| C 缺口补拍 | 合格原片、来源及操作记录 | 需要的画面真实、清晰、已备份 | 具体缺失镜头 |
| D 全片编排 | 完整时间轴、局部预览 | 内容连续、节奏与样片一致 | 受影响镜头和邻接转场 |
| E 交付验收 | 最终 MP4、工程包、验收记录 | 技术与视觉分别合格，限制明确 | 失败所属层 |
| F 恢复与关闭 | 精确恢复结果、资源释放记录 | 本次数据及衍生残留已核对 | 本次恢复缺口 |

全新项目若没有任何可用素材，可先按 C 的安全要求做 1-2 个样片必需界面的最小采集，再回 B；不要把它扩大成全业务流程准备。

C 完成素材备份与覆盖检查后，应尽早执行 F 的数据恢复，不必让演示数据一直保留到 E。F 的最终核对仍属于任务关闭条件。若完全复用旧素材且没有写入，记录“无新增数据操作”，不重复旧清理。

## 2. 上轮教训与对应改法

可核对的基线来自[T-393 工程说明](../../video/beckon-launch-60s/README.md)和[原执行计划](../superpowers/plans/2026-09-15-beckon-launch-video-plan.md)。本地细节证据在该工程的 `qa/review.md`、`qa/*-technical.json`、`capture/manifest.json`，其中部分被 Git 忽略，不假定新 checkout 自带它们。

| 已发生的问题 | 根因 | 本流程中的具体改法 |
|---|---|---|
| 用户认为画面太平，转场与起伏不足 | 固定左右构图、静态截图与淡化占主导；技术样片被当成视觉样片 | B 先验最难连续段；检查构图、尺度、动势及停顿，不以 lint 代替审美 |
| 大量拍摄准备发生在视觉方向验证前 | 把业务状态齐全当成动效设计的前置条件 | 用已有真实截图做样片；只为样片的必要缺口做最小补拍 |
| 排班、时区、匹配、报价存活期、完成时间等约束逐个暴露 | 缺少一次性的数据预检与状态依赖图 | C 集中检查所有前置条件；真实等待移出主要制作路径 |
| 插表被拒、宠物类型等字段不合法 | 未先核对当前公共操作与分类约束 | 复用现有服务/RPC和数据契约；写入失败后读原因，不猜字段继续写 |
| 错页、加载态、遮挡控件被拍入；模拟器前台被其他任务抢占 | 将屏幕坐标、旧元素引用与“当前设备”当成稳定定位 | 固定 UDID、账号与 build；界面变化后更新定位，拍后立即验收 |
| 22 张截图中最终引用 13 张 | 既有合理备份，也有错页和未就绪素材；并非 9 张全属浪费 | 镜头与素材一一映射；备份必须有用途，不为凑数量采集 |
| VFR 素材截段长度异常 | 未先统一帧率和时间戳，再进入剪辑 | 先探测、归零、转 CFR，再按帧截段；一条通过后批处理 |
| 完整片才发现发布成功停留过短 | 抽帧可见不代表正常速度可读 | 样片及局部都正常速度播放；关键结果留足稳定阅读时间 |
| 大段渲染日志、完整界面树和 JSON 进入上下文 | 工具输出未分层，反复读取不变信息 | 原始日志落盘脱敏；只返回结论、错误及定位所需上下文 |
| 浏览器直接播放完整 MP4 持续缓冲 | 把播放器路径问题与成片编码混为一谈 | 先用本机播放器和完整解码验证；浏览器只承担其必要的预览/交付职责 |
| 首次清理后仍有队列残留 | 异步衍生数据尚未收敛 | 有界只读复核本次记录，保留残留事实；不强制清空全局队列 |

上轮从建工程到完成提交约 101 分钟；两次全片渲染分别约 106 秒和 110 秒。口径不含此前规划和调研，不能当成总投入或长期速度承诺。没有逐步骤 token 计量，因此不编造占比或节省百分比。优先减少返工和重复上下文，不削弱隔离、真实性与恢复。

## 3. A：一次性确定范围

把以下内容写入一份 `production.md`，不要分别建立内容重复的计划、日报和总结：

- 目的与受众：演示核心体验，还是逐步教学；一分钟内只传递一个主张及少数支撑点。
- 成片约定：时长、画幅、分辨率、帧率、标题语言、原生 UI 语言、声音与播放场景。既有 Beckon 版本是 60 秒、16:9、1080p、30fps、中文介绍、英文 UI、完全静音；这是可继承的项目条件，不是所有视频的默认规格。
- 验收方式：用户先看样片，还是已委托自主推进；后一种先做明确的自检结论，交付时仍不得声称用户已认可审美。
- 素材范围：哪些界面必须真实、哪些只是外层介绍图形、哪些照片可生成；不允许生图伪造 App 界面、订单、评价或成功结果。
- 操作范围：账号别名、允许的数据类型、设备占用、恢复办法及授权来源；只记录引用，不记录凭据。
- 交付范围：本地成片、可编辑工程、是否云盘上传。上传目的地和访问权限另核对，不默认公开分享，也不把介绍视频当成可安装 iOS 包。

只有缺失且会改变制作结果或安全边界的信息才询问。已明确授权范围内不重复征询；用户说“全权处理”也不扩展到其他任务账号、生产数据或平台禁止的操作。

### 素材复用与工具选择

先以文件清单、manifest 和少量缩略图检查旧素材。UI、品牌、文案或业务事实已变化时标记失效，不为省事继续宣传旧能力。未变素材保留其来源证明与校验值。

| 情况 | 路径 | 需要的新证据 |
|---|---|---|
| 已有 Hyperframes 工程，仅调整文案、节奏或动效 | 优先局部改现有工程 | 变化镜头与连接处的动态预览 |
| 需要丰富的发布会式镜头，愿意采用 Remotion | 先评估 video-shotcraft 的具体镜头实现 | 真实素材样片、字体/依赖/渲染可运行性 |
| 缺少真实交互过程，且交互本身是卖点 | 补录关键动作，周边用已有截图 | 真实结果、录制完整性与恢复记录 |
| 只有非关键宠物照片或头像缺失 | 在授权内生图，再作为真实演示资料使用 | 图像来源、上传结果与精确清理 |

不要为了“换工具”重做已通过的素材层，也不要为保住旧工程牺牲已确定的视觉目标。引擎选择在样片阶段完成；迁移意味着新样片验证，不默认双引擎长期维护。

[video-shotcraft 官方仓库](https://github.com/Vincentwei1021/video-shotcraft)提供基于 Remotion 的镜头配方、动画实现和模板。使用时从[官方镜头库](https://vincentwei1021.github.io/video-shotcraft/library.html)选具体样式，核对对应实现与授权/许可，记录版本和参数，再替换品牌与真实 UI；不要仅凭配方名字重新猜一套动画。它不是自动保证成片质量的模型。本次文档整理未安装或验证其本地渲染链路。

外部技能、模板和示例只是工具资料，不覆盖用户需求、宿主权限和仓库规则。模板有配乐不代表静音任务可以加音乐；外部流程要求子代理也不覆盖本仓库禁用子代理的约束。

## 4. B：先做真正的动效样片

### 4.1 先写镜头，不先写页面

每个镜头记录：时间段、唯一信息、真实素材 ID、起始/结束构图、视线焦点、进入/退出方式、稳定阅读区间及与下一镜的连接。宣传文字与真实 UI 分层，不能覆盖价格、日期或状态来篡改事实。

下表是 60 秒片的节奏起点，不是强制逐秒照搬的最终脚本：

| 时间 | 信息职责 | 动态与停顿 |
|---|---|---|
| 0-5 秒 | 产品名及一个明确价值 | 简洁而有力量的揭示，迅速落到产品 |
| 5-14 秒 | 对象与需求 | 从主体过渡到真实界面，建立上下文 |
| 14-25 秒 | 发起请求 | 用连续运动串起必要步骤，压缩等待而非关键确认 |
| 25-39 秒 | 比较选择，主要展示段 | 全界面到局部特写再回整体；比较时稳定停留 |
| 39-48 秒 | 确认与结果 | 真实操作形成第二个重点，成功后明确停顿 |
| 48-55 秒 | 沟通及服务后的价值 | 降低运动强度，区分另一笔历史记录 |
| 55-60 秒 | 品牌与一句总结 | 动势收束，留可读的结尾 |

不要等间隔地切换标题和手机截图。节奏来自信息密度、画面尺度、动作速度与静止时长的对比；静音片也必须有起伏，不能靠未来添加音乐补救。

### 4.2 选择最能暴露问题的一段

优先选“比较报价 -> 选择 -> 确认结果”这类连续 12-15 秒，而不是只有 Logo 和开场标题的简单片段。素材不足时用现有真实 UI 演示同一镜头语法，明确哪些内容不是最终段落；占位图只能用于标注过的布局草稿，不能作为真实 UI 样片通过。

先写出至少三个有理由的视觉变化，例如整体手机进入、真实报价局部特写、视线匹配到确认结果。接着渲染低成本动态预览并正常速度看完，再输出目标分辨率样片检查文字。不要只看几个静态帧。

### 4.3 样片检查表

- [ ] 去掉声音后，观众仍知道当前在解决什么、该看哪里、动作带来什么结果。
- [ ] 全界面与局部特写有明确尺度变化；不是一直固定左文右手机。
- [ ] 至少有一处有意义的场景连接和一处清晰的收束停顿，不是每次都淡入淡出。
- [ ] 运动在阅读时让步；价格、时间、确认结果不会边高速移动边要求读清。
- [ ] 有快慢对比，但没有为“高级感”持续摇晃、旋转或堆叠多个焦点。
- [ ] 转场方向、出入位置与视线连续；遮罩/缩放/匹配切换用于说明关系，不随机轮换特效。
- [ ] 标题与真实 UI 在目标播放尺寸可读；手机比例不变，未重复绘制原片已包含的刘海或岛形区域。
- [ ] 品牌颜色、字体与 UI 一致；模板皮肤没有压过产品本身。
- [ ] 对照参考说明哪些手法已经实现，哪些仍未达到，而不是只写“看起来不错”。

作为初始调参值，信息标题可先留约 1.5-2.5 秒稳定阅读，价格/时间比较约 2.5-4 秒，关键成功状态约 2-3 秒；这些是工作假设，最终以实际文案和正常速度观看为准。快转场后一定给视线落点。不能用累计出场时长掩盖几乎没有稳定阅读时间的问题。

样片记录三项独立结论：`信息：通过/待改`、`视觉：自检通过/用户通过/待改`、`技术：通过/待改`。任一核心项待改就不批量扩片。需要用户审美确认时只请求对这一个样片给反馈，不重复询问已经授予的操作权限。

## 5. C：缺什么才准备什么

### 5.1 业务与环境预检

只有确实缺素材才进入本节。先读对应的[TestOps 入口](../04_ios/testops/README.md)和当前业务契约，建立最小状态依赖图，例如“宠物 -> 请求 -> 两份有效报价 -> 接受 -> 预约 -> 对话”；评价来自另一笔合法已完成服务时，在镜头中说明。

| 一次预检项目 | 写入前要确认的事实 |
|---|---|
| 账号与设备 | 账号、模拟器均未被其他任务占用；角色与归属正确，权限来源明确 |
| 资料与分类 | 宠物/服务类型使用当前合法值，资料满足匹配要求，已有合格照片可复用 |
| 排班与时间 | 排班窗口、时区及 NULL 语义、服务时长、缓冲、提前量、当天限制和占用 |
| 请求与报价 | 匹配资格、请求可见性、报价最短有效期、接受截止及确认时仍有效 |
| 完成与评价 | 真实开始/完成条件、实际时间约束、评价资格；不能修改系统时钟或伪造历史 |
| 操作入口 | 当前公共 API/RPC、既有安全脚本及失败语义；不绕过 RLS、触发器或约束 |
| 回滚能力 | 基线完整、新增 ID 可识别、依赖顺序明确、图片与衍生数据有恢复办法 |

预检不能保证所有动态约束永远不变；接受、开始、完成等操作前仍核对关键实时条件。授权不覆盖所需动作时，先继续可做的离线部分，不拿其他任务授权补足。

### 5.2 精确准备，不进行全库铺数

1. 先写待变更清单、前置条件和恢复顺序，保存只含本次必要记录的本地基线，权限限于必要人员。保留 NULL 与空值区别，不保存令牌。
2. 通过已有公共业务入口创建最少演示数据。写前记录意图，写后记录返回 ID 和结果；尽可能复用现有幂等/回执能力。
3. 网络超时或结果不明时，先按回执/精确对象读取实际结果。发布、接受、评价等不可逆动作不得直接重试来“确保成功”。
4. 同一约束错误再次出现前必须有新诊断或修正。不要逐个猜时间窗口、类型值或字段再碰运气。
5. 将必须真实等待的历史服务尽早安排在允许时段，等待期间做离线编排。若不是镜头必需，优先采用已有合法历史记录，不为一秒画面制造长等待。

### 5.3 稳定拍摄

- 固定设备 UDID、分辨率、系统版本、bundle、build 来源与校验值。复用兼容构建，不为每个镜头 rebuild；构建变化时重新评估受影响的旧素材。
- 账号隔离与设备隔离分别成立。Xcode 写入和 linked CLI 遵守原有串行规则；遇前台争用优先使用明确 UDID 的采集，不盲目点击别人的窗口。
- 默认一台设备串行切角色；只有确实减少反复导航且资源允许时用第二台。不要以“并行”为由抢占验收设备或增加内存压力。
- 可逆步骤可预演；提交前停止预演。正式录制保留动作前后各至少约 1 秒、关键结果至少约 3 秒余量；不可逆动作只做一次，补拍结果页或延用真实静帧。
- 弹窗、滚动、键盘、页面加载后重新获取定位；先确认控件可见且未被页脚遮挡，再操作。不能复用陈旧引用或单凭坐标连点。
- 使用原始分辨率 PNG/录屏，工具返回的缩小预览只用于定位。当前页标题、关键字段、加载状态、键盘、遮挡和敏感资料都合格后才保存为可用素材。
- 每条拍完立即看关键帧并挂到镜头 ID；坏素材标记原因，不拖到剪辑时才发现。只有明确用途才留备选，原片不覆盖。

以下是命令结构，不内置旧设备 ID。变量必须来自本次已核对的设备、输出路径和授权：

```bash
xcrun simctl io "$VIDEO_SIM_ID" screenshot "$VIDEO_STILL_PATH"
xcrun simctl io "$VIDEO_SIM_ID" recordVideo --codec=h264 "$VIDEO_RAW_PATH"
```

录屏使用可控会话，结束时只停止本次录制并等待文件写完；不要 kill 整个 Simulator。生图仅补授权的虚构照片/头像，保留来源；需要在 App 中出现时走正常上传，再拍真实界面。

## 6. 素材处理与来源

每条媒体先用本地已安装的 `ffprobe` 读取时长、帧率、帧数、尺寸、像素格式和色彩信息，不能把工具版本或上一条素材的属性当成当前事实：

```bash
ffprobe -v error -show_streams -show_format -of json "$VIDEO_RAW_PATH"
```

处理顺序：**原片只读 -> 探测 -> 时间戳归零与目标 CFR -> 验证 -> 按帧截段/拼接 -> 片段验证 -> 合成**。

- Simulator 录屏可能是 VFR。先在派生副本转换为目标恒定帧率，再以帧区间剪辑；不要靠平均帧率推算原片帧号。
- 对第一条素材验证时长、帧数、关键事件和尾部，再沿用同一已验证处理方式。截段后重置片段时间戳，明确区间为 `[startFrame, endFrame)`。
- 区分真实颜色转换和仅修改编码标签。T-393 原片是 sRGB transfer 配合 BT.709 primaries/matrix，后续输入不一定相同；只有探测与来源确认后才选择对应转换。遇未知标签先诊断，不盲目套用旧滤镜。
- 保留原始比例，裁切记录原像素坐标；放大真实区域，不重绘或替换价格、时间和状态。历史记录与独立补拍的关系在画面或说明中明确。
- 关键帧间距按实际引擎的 seeking/预抽帧需求选择，避免未经验证的稀疏关键帧配置。一条片段验证通过后再批量处理。
- 原片、派生媒体与合成输出分别存放；变更派生媒体时更新 hash 和引用检查，不覆盖已交付版本。

最小来源字段：`assetId`、相对路径、SHA256、截图/录屏/生成分类、尺寸、时长与色彩、buildRef、角色别名、拍摄时间、镜头 ID、源区间、裁切和关键事件。业务内部 ID/设备及账号对应关系只放私有 manifest；可移交 manifest 应移除登录资料、敏感标识和不必要的原始元数据。画面本身也必须审查，不能只脱敏 JSON。

## 7. D：用同一套镜头语言扩展全片

采用一个制作工程、一套锁定依赖、一份逻辑时间轴。环境信息记录实际 Node、渲染器、浏览器、FFmpeg 与字体版本；使用项目本地 CLI及当前帮助，不反复用未锁定的 `npx latest`。

1. 用整数帧描述镜头长度和全片时长；60 秒、30fps 对应 1800 帧。转场重叠与逻辑段落分开记录，不能把重叠尾巴再次加进总时长。
2. 建立少量共享的文字、手机框、遮罩、镜头运动与转场参数，不搭一个通用视频平台。场景改内容，共享逻辑管一致性。
3. 所有动画可按时间/帧确定性重放；不要依赖真实播放起点、未固定随机数、网络加载时机或 DOM 未完成状态。
4. 预览与最终渲染引用同一素材/参数。字体、本地图片、视频及子合成路径必须可解析；动态素材以目标引擎真实渲染结果核对。
5. 根据样片的运动幅度、加减速、标题节奏与停留扩展场景。每段只有一个主要焦点，镜头连接必须说明信息关系。
6. 先检查改动段与前后相邻转场，再检查全片。共享字体、时间轴、全局颜色或引擎变化会扩大影响范围，不能仍称为局部改动。

默认沿用经过样片验证的并发配置；低内存机器可从单渲染 worker 开始。只有真实瓶颈是渲染且测量有收益时才调并发，不把机器型号当成必须多 worker 的理由。缺少与本片无关的配音/音乐工具不是静音片阻塞。

## 8. E：分层验收，不让一项替另一项过关

### 8.1 局部变更检查范围

| 改动 | 重新检查 | 可保留的证据 |
|---|---|---|
| 单镜头文字或位置 | 该镜头动态播放、布局与前后连接 | 未变素材真实性和数据恢复 |
| 单条截段 | 该条完整解码、帧数、事件、稳定停留及所在转场 | 未变场景构图与 UI 来源 |
| 共享样式/字体/引擎/全局时间轴 | 全片关键帧、边界、运行与动态节奏 | 仍匹配的原片来源证明 |
| 重新拍摄 | 新来源、业务关系、媒体属性、对应画面 | 无关旧镜头的有效证据 |
| 每次最终交付文件 | 文件级探测、完整解码、正常速度全片观看及 hash | 未受影响的分项检查记录 |

已有 T-393 `qa/verify.mjs`、`verify-source.mjs`、`review-frames.mjs`可作实现参考，但位于本地忽略目录，而且带有固定文件名、帧数与白帧规则。新工程必须按实际规格适配后再用；不能运行旧验证器，验证了旧文件却宣称新片通过。

### 8.2 技术门

对实际准备交付的文件执行探测和完整解码，保存退出码及错误日志。以下只验证媒体属性/可解码性，不会自动验收动效质量：

```bash
ffprobe -v error -count_frames -show_streams -show_format -of json "$VIDEO_FINAL_PATH"
ffmpeg -v error -xerror -i "$VIDEO_FINAL_PATH" -f null -
```

- [ ] 输出文件与交付版本一致；时长、尺寸、帧率、总帧数、codec、pix_fmt、色彩和音轨符合本片约定。
- [ ] 完整解码无错误，MP4 faststart 符合交付需要，素材引用无缺失，字体正确加载。
- [ ] 每段至少一个代表帧、复杂镜头的极值/中点和所有转场前后若干帧已检查；单帧通过不能替代运动检查。
- [ ] 黑/白/空帧扫描的发现逐项解释；只有已设计的帧区间可列白名单，不能为了通过检查放宽阈值。
- [ ] 无意外文字叠压、被裁断、变形或额外设备装饰；在目标播放尺寸检查主标题和需要读清的 UI 信息。
- [ ] 实际最终 MP4 正常速度从头播到尾并结束；工具错误、警告和跳过项都有具体结论。

### 8.3 视觉与真实性门

- [ ] 开头迅速交代产品，主要卖点有重点展示；结尾有可读停留。
- [ ] 全片存在快慢和尺度对比；不是用持续运动或堆特效掩盖平均的节奏。
- [ ] 每个信息点在正常速度下可理解，转场既连贯又不会遮住关键操作/结果。
- [ ] 画面仍以产品为主；模板、宠物装饰、标题和运动没有抢走核心 UI 的注意力。
- [ ] 名称、价格、时间、人物、请求/报价/预约关系一致；另一个历史服务不冒充刚完成的当前流程。
- [ ] 再与样片及用户反馈对照，明确哪些意见已落实。技术全绿仍可判定视觉待改。

播放路径分开判断：本地 MP4 优先 QuickTime 或已验证播放器；浏览器用于可编辑时间轴。浏览器直链缓冲时先查文件/解码/本机播放，不据此反复重渲染。若用户明确要求网页或云盘播放，它仍是单独交付条件，不能用本机播放替代。

## 9. F：恢复、打包与交付

1. 补拍完成后先确认素材覆盖镜头、文件可读且已有备份，再及时清理演示状态。复用素材任务跳过不存在的数据清理。
2. 清理仅按本次操作记录中的精确 ID、所有者、预期当前状态和依赖关系执行；共享对象后来被他人修改时先保留并诊断，不强行还原旧快照。
3. 恢复原排班、偏好、服务及可恢复资料的完整业务值，包括 NULL；不要倒改合法时间戳或 revision 伪装成从未发生过操作。
4. Storage 通过正常 Storage 接口处理精确对象，不只删表行。按实际系统检查本次私有上下文、派生投影、候选与队列残留。
5. 异步队列未归零时保留事实，按系统预期窗口进行有界只读复核。超出窗口后定位原因，不能无限轮询、强制清全局队列或宣布恢复成功。
6. 只关闭自己占用的模拟器、录制和临时服务；不 erase 共享设备。留给用户的预览服务可继续运行，但记录实际 URL 与停止方式。
7. 用允许清单打包可编辑源码、锁文件、必要素材、脱敏来源和复现说明。排除凭据、恢复基线、登录脚本、内部账号关系、原始敏感日志、`node_modules`和无用中间渲染。
8. 校验 ZIP 完整性，检查解压后的相对路径/素材引用及已安装依赖下的离线来源检查。记录是否真正执行过独立重渲染；未执行就不称其完全可复现。重分发字体、模板和第三方素材前核对许可。
9. 交付明确的最终文件、工程包、实际验证结论和剩余限制。内部版本号不代表用户已接受，已生成不代表已上传。云盘上传后按指定身份和权限验证下载，未经授权不开公开分享。

只改视频/文档时，不重跑无关 iOS 或后端全回归；若确实修改产品代码，则回到对应风险级别的开发验证，不能用视频验收替代它。

## 10. 时间、Token 与失败恢复

### 10.1 分配与记录

把下列比例作为启动时的**人工工作量规划**，不是测速承诺：范围及素材盘点 10%，脚本与样片 30%，缺口补拍 20%，全片编排 25%，验收恢复与打包 15%。没有补拍时，将其预算转给视觉打磨；外部等待与机器渲染单列。实际安全恢复工作不得为了符合比例被压缩。

- 每阶段只记开始/结束、有效产物、阻塞与返工原因。可以核对墙钟耗时；没有工具级 token 数据就写“未计量”，不猜测。
- 样片阶段发现视觉方案不成立，先改镜头设计；不要靠扩大工程来补救。素材准备明显超预算时，重新审视镜头是否真需要该状态。
- 一次性排查完整前置条件、一次性处理同类媒体；并行仅用于允许且无共享写入竞争的工作。Xcode、linked CLI 和不可逆业务序列不抢跑。
- 每轮修正只改变可定位的一组变量，并保留对比；到达可读、真实、风格一致的验收标准就交付，不无边界追加装饰。

### 10.2 上下文与日志

- 工具调用只取所需字段。完整渲染日志、界面树和探测结果落到受控本地文件，输出摘要与定位路径；日志本身也必须脱敏。
- 失败时返回错误类别、关键数行和相关对象状态，不把全量 SQL/账号清单/所有截图再灌入上下文。
- 媒体预览先看缩略索引，再展开失败镜头；不要反复读取未改变的整套源文件和完整录屏。
- 运行状态只保留当前阶段、下一步、产物路径和未决风险。时间轴只管帧，manifest 只管来源，恢复文件只管数据，不复制成多份真相。
- 等待真实工具完成使用其会话/等待机制；用户更新说明新增事实或当前产物，不重复未变状态。任务恢复读状态和指向文件，不从全部聊天重建历史。

### 10.3 失败时的最短回路

| 现象 | 下一步 | 禁止的无效重复 |
|---|---|---|
| UI 操作未生效或点到别处 | 重取当前状态，检查遮挡、展开控件、滚动和设备身份 | 旧坐标连点、反复提交 |
| 写入被拒或结果不明 | 读约束/回执与精确对象，定位前置条件后再操作 | 猜参数、绕权限、重建账号 |
| 录屏截段长度不对 | 检查 VFR、起点、归零、CFR及帧区间 | 直接拉长合成时间掩盖素材不足 |
| 预览好而导出坏 | 固定帧比较字体、素材路径、视频解码和确定性 | 无诊断地全片重渲染 |
| 画面仍显平淡 | 重看样片焦点、构图尺度、连接与停顿 | 给每段再加同一种淡化或弹跳 |
| 浏览器视频缓冲 | 先探测/完整解码/本机播放，单独查交付路径 | 重写动画或反复压片 |
| 缺失全局安装/写入/网络权限 | 在允许范围继续已有工具和离线工作，清楚报告受限项 | 绕过沙箱、重复权限请求或伪称后台继续 |
| 复核发现恢复残留 | 查本次对象与异步收敛，报告具体未恢复项 | 抹掉记录、全库清理或宣布完成 |
