## 1. 1.0 完成定义（Definition of Done）

同时满足以下全部条件，方可宣布 1.0：

1. **无半成品交互**：App 内不存在占位 tab、假按钮、填了不存的表单字段。
2. **图片可见**：宠物照片、美容师作品集、头像在授权范围内可正常渲染。
3. **市场闭环有时效性**：4 类关键事件（新匹配、新报价、报价被接受、新消息/取消）有推送；聊天前台实时。
4. **状态机自洽**：48 小时过期真实执行；取消后有再发布路径；补匹配机制生效。
5. **审核合规**：账号删除、隐私政策、Privacy Manifest、支持页齐备。
6. **质量达标**：≥200 个单元测试全绿（含边缘用例），核心旅程 UI 测试通过，崩溃上报接入，TestFlight 公测 ≥1 周无 P0/P1 缺陷。
7. **边界不破**：Open Request -> Groomer Offer -> Customer Confirmation -> Booking 模型不变；SwiftUI 不直连 Supabase；远程 DDL/数据写入逐任务显式授权。

**明确不进 1.0：** 支付/托管、订阅、地图优先、AI 推荐、多宠物请求、收藏夹、聊天附件、已读回执、美容师回复评价、请求编辑、Admin 后台、社交登录。

### 6.2 边缘用例清单（T-070 执行基准）

**时间与时区（重点，当前完全缺失）**
- 向导时间预设（Morning/Afternoon/Evening/Flexible）在临近午夜选"今天"时的跨天行为。
- 设备时区 ≠ 服务地时区时，preferredStart/End 的持久化与回显一致性。
- DST 切换日（时钟拨快/拨慢）生成的时间窗仍满足 start < end。
- 预约重叠边界：首尾相接（end_a == start_b）必须判定为**不冲突**（与数据库排他约束语义一致）。
- 48 小时过期边界：恰好 48:00:00 的请求状态判定。
- 过去时间：向导选择已过去的时段应被拦截；报价 proposed range 在提交瞬间刚好过期。

**字符串与输入**
- 空、纯空白、首尾空白（trim 语义）：显示名、宠物名、服务标题、评价内容、聊天消息。
- 超长输入：报价留言/评价内容达到与超过后端长度上限（上限 ±1 三点测试）。
- Emoji、组合字符（é）、CJK、RTL 文本在名称与消息中的长度计数与渲染安全。
- 聊天消息纯空白拒发；发送失败后重试不产生重复。

**数值边界**
- 报价价格：0、负数、下限、上限、上限 +0.01、超两位小数（scale 校验）、非数字输入。
- 评分：0、1、5、6（1~5 闭区间外必须拒绝）。
- 三条开放请求限制：第 3 条成功、第 4 条被拒且错误文案正确；取消一条后可再发。
- 照片快照上限：第 20/21 张照片元数据边界（后端截断 20 的契约回归）。
- 服务半径 clamp（现有向导 clamp 逻辑的下/上界外输入）。

**集合与状态**
- 空列表：无宠物发请求（向导第一步拦截）、无匹配、无报价、无预约、无会话的空态。
- 单元素/多元素分组：报价 pending 与 history 分组各自为空/混合时的展示。
- 重复操作幂等：重复取消同一请求/预约、重复完成预约、重复接受已接受报价——Store 对后端幂等/拒绝结果的处理。
- 列表中目标已消失（他端已取消/已过期）时的动作失败恢复：本地状态回滚 + 错误提示 + 刷新。

**权限与会话**
- 登出后 Store 清理：无残留他人数据（切换账号场景）。
- Repository 返回权限错误（RLS 拒绝）映射为可理解文案而非原始错误。
- 角色错配防御：customer 会话调用 groomer 动作路径的前置拦截。

**新功能同步覆盖（随 M1/M2 任务红/绿交付）**
- T-050：签名 URL 过期/获取失败的占位与重试；缓存命中不重复请求。
- T-051：地址/半径持久化的往返（发布→详情回显→美容师侧快照）一致性。
- T-052/T-058：过期与补匹配后，客户卡片、美容师 feed 的过滤正确性。
- T-056：device token 注册/注销时机（登录/登出）。
- T-060：已读落库后跨"设备"（新 Store 实例）可见性。
- T-061：删除后本地会话与各 Store 的清空。

## 9. 执行约定（对齐 T-049 后的现行工作流）

- **一次运行只做一个主任务**；不自动开始下一个任务（台账规则）。
- 每个任务启动时从 `docs/06_tasks/TASK_LEDGER.md` 领取下一个可用编号；Standard/Deep 任务建立独立任务文档，Micro/Quick 文档类工作默认不建。
- 改变应用行为、后端行为或持久工作流状态的任务，完成后更新台账与 `docs/00_memory/WORKLOG.md`；仅当未来运行需要该事实时更新 `docs/00_memory/CURRENT_STATE.md`；持久记忆/台账变更后运行 `node scripts/context-hygiene-check.mjs`。
- 所有远程 Supabase DDL/数据写入仅经 Supabase MCP，逐任务显式授权，迁移镜像至 `supabase/migrations/`，并同步 `docs/03_backend/SUPABASE_CONTRACT.md`。
- 涉及后端的任务（T-051/052/056/058/060/061）均需 advisors 复查 + 回滚式验证，不留未审阅告警。
- 产品模型红线不动：Open Request -> Groomer Offer -> Customer Confirmation -> Booking；不重新引入任务卡推送流。
- 本计划中的新屏幕（Offers tab、通知落点）实现前先登记 `docs/01_product/SCREEN_INVENTORY.md`；新后端状态先写入 `docs/03_backend/SUPABASE_CONTRACT.md`。
- 提交、推送、打 tag、建 PR 一律需用户显式批准。
