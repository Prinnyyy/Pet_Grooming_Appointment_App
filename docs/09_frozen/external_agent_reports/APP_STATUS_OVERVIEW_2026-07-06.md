## 1. 产品定位

**Pet Groomer Marketplace**（UI 品牌名 **Groomly**）是一款 iOS 原生宠物美容预约市场应用：

> 宠物主人发布一条公开美容请求 → 系统匹配符合条件的独立美容师 → 美容师主动报价 → 宠物主人确认一份报价 → 生成预约（Booking）→ 服务完成后评价。

核心产品模型（不可变更的产品铁律，见 `docs/01_product/PRODUCT_BRIEF.md`）：

```text
Open Grooming Request（公开请求）
-> Matched Groomers（系统匹配）
-> Groomer Offers（美容师报价）
-> Customer Confirmation（客户确认）
-> Booking（预约）
```

与传统"客户逐个联系美容师"模式的差异化：**客户只描述一次需求，供给侧主动竞价**。这是本产品的核心价值主张，也是所有后续迭代必须保护的模型（不得重新引入任务卡推送流）。

### 目标用户

| 角色 | 描述 | 核心任务 |
|---|---|---|
| Customer（宠物主人） | 维护宠物档案，发布请求，比较报价，管理预约 | 一次发布、多方比价、安心履约 |
| Groomer（独立美容师） | 维护档案/服务/作品集，浏览匹配请求，报价接单 | 只对感兴趣的请求出手，管理履约 |
| Admin | **明确推迟**，无管理后台与审核流程 | — |

### 2.2 架构现状（健康）

分层清晰，边界纪律执行到位：

```text
SwiftUI View（Features/*，保持轻薄）
  -> Store（@MainActor 状态所有者，每个功能域一个）
    -> Repository 协议（Core/Repositories）
      -> Supabase 适配器（Core/Infrastructure/Supabase）
        -> Supabase（Postgres + RLS + RPC + Storage）
```

- **SwiftUI 视图不直连 Supabase**，全部经过 Repository 边界（已验证执行到位）。
- 关键状态转换全部走**服务端 RPC**（`security definer` + 空 `search_path` + 显式授权），客户端不做权威裁决；RLS 与 Data API 显式授权双重控制。
- 业务不变量在数据库层强制：每用户单角色（不可变）、每客户最多 3 条开放请求、每请求/美容师至多一条待定报价、每请求至多一个 Booking、美容师已确认预约**时间不重叠**（`btree_gist` 排他约束，允许首尾相接）、每完成预约仅一条客户评价。
- 设计系统完备：`DesignTokens.swift` + Groomly 动作/反馈/表单原语，全部已实现 MVP 屏幕完成 Groomly 视觉改版；后续 UI 变更遵循"截图驱动"工作流。
- 后端契约、RLS/RPC 策略、Storage 策略均有活跃文档（`docs/03_backend/`），与已部署迁移保持同步。

| 运维/合规 | 净化后的 Debug Panel；密钥管理纪律良好（凭据类文件不读不提交） | 无账号删除（App Store 硬性要求）、无 Privacy Manifest、无崩溃上报、无分析埋点 |

## 3. 产品经理评审：不合理之处与改进意见

以下按对 1.0 上线的伤害程度排序。

### P0 — 不修复不能上线

**① 照片"能传不能看"是体验欺诈级缺口。**
宠物美容是强视觉决策品类：美容师靠作品集获客，客户靠宠物照片传达需求。当前用户可以上传照片、看到元数据行，却永远看不到图像本身。这比"没有照片功能"更糟——它承诺了又违背。
**改进：** 1.0 必须实现私有 bucket 的签名 URL 获取 + `AsyncImage` 渲染 + 缓存，覆盖宠物照片、作品集、头像三处。

**② 向导收集但丢弃用户输入，损害信任。**
五步向导让用户填写位置模式、街道地址、服务半径、上传照片，但这些字段发布后**静默丢失**。用户以为美容师能看到地址和照片，实际看不到——上门服务场景下这会直接造成线下履约纠纷。
**改进：** 二选一，且必须在 1.0 前决断：(a) 后端补齐字段持久化与快照（推荐，地址对上门服务是刚需）；(b) 从 UI 移除未持久化控件。**绝不允许"填了不存"带到正式版。**

**③ 无通知的双边市场无法运转。**
报价何时到、报价是否被接受、预约是否被取消、有没有新消息——当前全部依赖用户主动打开 App 手动刷新。双边市场的流动性建立在响应速度上：美容师晚看到请求就少接一单，客户晚看到报价请求就过期。这是 1.0 最大的留存/流动性风险。
**改进：** 1.0 必须交付 APNs 推送（4 类关键事件：新匹配请求、新报价、报价被接受、新消息/取消），配合应用内刷新。

**④ 账号删除是 Apple 审核硬门槛。**
App 支持账号注册，App Store 审核指南 5.1.1(v) 强制要求提供账号删除入口。当前没有，**提审必被拒**。
**改进：** 设计删除 RPC（数据清理策略：个人资料匿名化 vs 级联删除，需兼顾对方参与者的预约/评价记录完整性）+ Account 页入口 + 二次确认。

**⑤ 48 小时过期是"纸面契约"。**
`expired` 状态在枚举和 RPC 校验里到处出现，但没有任何机制真正把超时请求置为过期。结果：过期请求永远显示为 `open`，美容师会对已死请求报价，客户列表被僵尸请求污染。
**改进：** 用 `pg_cron`（Supabase 支持）定时执行过期转换（请求 + 报价 + 匹配联动），iOS 侧正确渲染过期态。

### P1 — 严重影响体验/增长，1.0 应修复

**⑥ 匹配是一次性快照，供给增长不反哺存量需求。**
匹配只在 `create_grooming_request` 执行瞬间计算。之后新入驻/重新激活/新增服务的美容师，都无法匹配到已存在的开放请求。冷启动期供给稀薄，这个设计会显著放大"发了请求没人报价"的死亡体验。
**改进：** 增加补匹配机制——最简做法是美容师激活/入驻时对现存开放请求跑一次匹配 RPC；或随过期定时任务周期性补匹配。

**⑦ Groomer Offers tab 占位符必须消灭。**
正式版 App 出现 "not connected yet" 占位 tab 不可接受。美容师也确实需要集中查看自己报价的状态（待定/被接受/被拒/已撤回/过期）。
**改进：** 实现"我的报价"列表（数据已在 `groomer_offers` 表，RLS 已允许美容师读自己的报价），工作量可控；若时间紧张则移除该 tab——但推荐实现。

**⑧ 邮箱确认流程是注册转化率杀手。**
注册 → 去邮箱 → 浏览器打开确认 → **手动回到 App 重新登录**。每多一步流失一批用户；且默认 SMTP 有严格限流，公测都撑不住。
**改进：** Universal Link 深链自动完成确认 + 配置生产 SMTP。

**⑨ 取消后的断头路。**
预约被取消后，请求和报价保持关闭（这是经审慎设计的后端语义，不动），但客户必须从零重新走一遍五步向导。被动被取消的客户是最需要安抚的用户，却拿到最差的路径。
**改进：** 1.0 提供"再次发布"：从已取消预约一键预填原请求数据进入向导确认步。完整改期/重新预约流程放 1.x。

**⑩ 聊天无实时性。**
预约后的沟通（确认地址、宠物状况）是履约关键期，手动刷新的聊天不符合 2026 年用户底线预期。
**改进：** 接入 Supabase Realtime 订阅 `messages`（参与者边界已由 RLS 保证）。推送（③）覆盖后台场景，Realtime 覆盖前台场景，互补。

### P2 — 应在 1.0 收敛的产品毛边

- **静态假通知铃铛**（Customer Home）：要么接通知，要么移除。正式版不留假交互。
- **交接卡已读仅存本机**：换设备/重装后已确认的交接卡再次弹出。应落库为客户级持久状态。
- **预约对方姓名缺失**：预约列表/详情看不到对方称呼，聊天场景尤其别扭。补充参与者展示名的安全读取路径。
- **评价单向且无回复**：1.0 可接受（客户评美容师是核心信任方向），但应在产品文案上明确规则；美容师回复放 1.x。
- **无崩溃上报/分析**：正式版发出去等于裸奔。至少接崩溃上报 + 关键漏斗埋点（请求发布、报价、接受、完成）。

### 明确建议不做进 1.0 的（防 scope 蔓延）

支付/退款、订阅、地图优先体验、AI 推荐、多宠物打包请求、收藏夹、聊天附件、已读回执、请求编辑、管理后台、社交登录（与 `docs/01_product/PRODUCT_BRIEF.md` 推迟清单一致）。1.0 定价策略建议：**平台不碰钱**，价格仅作为报价信息展示，线下结算，App 内明确免责声明——避开支付审查复杂度与资金合规问题。

## 6. 结论

这个项目的工程纪律远超一般 MVP 水准：分层边界、数据库不变量、RLS/RPC 安全模型、迁移追溯、文档同步（T-049 后进一步索引化瘦身）都非常扎实，**技术地基可以直接承载 1.0**。

真正的差距在产品完成度的"最后一公里"：图片渲染、通知、字段持久化、过期任务、账号删除——这些不是架构问题，而是被有意推迟的功能债。它们共同的特征是：**单独看都不大，但任何一个带进正式版都会在真实用户面前击穿产品可信度或直接卡死审核。**

建议按配套的《V1.0 正式版交付任务计划表》执行（任务编号自 T-050 起，与任务台账衔接），预计 8~10 周可达成可提审的 1.0。
