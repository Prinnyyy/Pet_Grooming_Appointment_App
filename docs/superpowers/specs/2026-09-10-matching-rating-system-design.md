## 1. 范围与判断原则

业务链路保持 `Request -> Matches -> Offers -> Customer Confirmation -> Booking -> Review`。顾客不逐个联系美容师，不引入公开目录、直接订时段、机器学习模型、隐式用户画像或新的客服裁决系统。

核心目标按优先级为：不越过明确约束；证据真实且口径一致；合法报价可被发现和比较；提高有效报价及履约效率。点击率、在线时长和订单量不是成功的替代指标。

| 路线 | 判断 |
|---|---|
| 只修旧总分 | 能修局部错误，但无法解决证据来源、跨物种能力迁移、分页排序和刷新一致性 |
| 分层规则与有限统计平滑 | 采用；适合当前数据、SQL/Swift 架构和可解释要求 |
| 行为学习或双边机器学习推荐 | 不采用；缺少可信曝光、归因与校准数据，会引入新的反馈偏差和维护成本 |

资格、证据、排序、成交确认是四个独立责任。低分不等于不能服务，高分不等于可接受报价，曝光不预留时间。分层结构可参考[推荐系统候选、评分与重排](https://developers.google.com/machine-learning/recommendation/overview/types)；本文具体公式与参数是项目设计，不是该资料证明的最优值。

## 2. 已知问题与本轮修正

前序审查已经核对当前数据库函数及触发器；证据复用，不重复远程验证相同定义。本次新增结论主要来自设计反例与针对性源码检查。

| 编号 | 问题或反例 | 本设计处理 |
|---|---|---|
| A1 | 评价只校验标签字典，不验证是否属于预约 | 服务端生成并冻结允许评价的上下文；提交只能取其子集 |
| A2 | 四舍五入后的均分再次累计 | 原始有效评价或准确总和/数量是唯一星级来源 |
| A3 | 评价、技能与作品变更未覆盖已有匹配刷新 | 分离资格、专业证据、整体评分、展示信息的失效范围 |
| A4 | `mat` 等子串错误生成护理事实 | 自由备注不生成资格或评价标签 |
| A5 | 无物种接受范围，猫狗共享专业证据 | 服务拥有明确物种范围，专业证据严格区分物种 |
| R1 | 将同一顾客的衰减权重直接归一到 1，会让多条旧评价在一段时间内不衰减 | 一名顾客的总影响上限随其最近相关服务的年龄一起衰减 |
| R2 | 只平均已填写的标签，可能把局部好评包装为完整专业适配 | 对请求适用的维度确定固定分母；未填写不冒充正面或负面 |
| R3 | 所有 `custom_request` 共享类型，但实际可能是完全不同服务 | 首版不在自定义请求之间迁移专业评分，不用文本相似度猜测 |
| R4 | 先取时间顺序一页再按分数排序，会漏掉后页更优候选 | 服务端对完整授权候选集排序后分页；引入版本校验，而非客户端局部排序 |
| R5 | 初稿“浏览中顺序固定”若不说明数据变化处理，会导致跨页重复或漏项 | 选择无持久浏览快照的版本化游标；版本变化明确要求刷新 |
| R6 | 以评价提交日或延迟确认完成日计算宠物年龄/证据新旧，可改变历史能力 | 固定于已确认服务时点；晚写评价不能给旧服务重新计龄 |
| R7 | 把所有失效都作为“匹配待校验”，会因一条新评价阻断合法成交 | 软评分故障不改变资格；报价和接受只依赖权威业务校验 |

R1-R7 是对已确认方向的完善，不是已部署缺陷修复。保留下述审查入口，后续发现更好的低复杂度路径仍可修订。

## 3. 输入、事实与所有权

### 3.1 请求与服务

- 以已发布 Request 的宠物、服务、地址和时间快照匹配，不能拿后来编辑的宠物资料重写请求意图。发布后的改变沿用版本化替换流程。
- 接受物种放在每个 `groomer_service` 上，作为唯一可写来源；Profile 如需汇总，只读展示服务范围的并集，不建立第二套覆盖规则。
- 物种范围 `null` 表示未确认，非空集合表示明确范围，空集合表示不接受任何物种。旧服务不能批量填成“猫狗都接受”；新启用服务必须确认非空范围。
- 宠物物种属于必需事实；旧请求缺失时要求顾客确认并替换，不能从品种文字猜测。体型、时长与护理细节未知仍可进入现有评估通道，但不得标为已知适配。
- 体型归一到现有 XS/S/M/L/XL/XXL/Giant。新数据若体重与选择的体型冲突，在提交时解决；旧冲突不择其有利值，标为待评估。毛型优先显式确认，不从不可靠品种猜测生成专业加分。
- 现有结构化性格、生日可按固定规则派生护理提示。新增毛发打结事实为明确确认值；旧备注仅展示，不自动转换成 true/false。护理标签不是医疗诊断或专业认证。

### 3.2 允许评价的上下文

在已接受的协议和可信服务记录上确定 `evidence_context_version`、物种、服务类型、服务时点和可评价的规范键；完成后不可随当前宠物/Profile 修改而漂移。若预约合法改期，使用最终服务协议的时点，不使用首次请求时间。

首版年龄及时间衰减统一取最终协议的 `scheduled_start`，按保存的服务地点时区计算年龄日期。它是可复核的约定时点，不冒称测得的实际开工时间。缺少可信历史服务时点时保留星级，但相关专业维度不计分；不得退回设备 `Date()`。

| 维度 | 规范键与适用条件 |
|---|---|
| 服务 | 已确认的固定服务类型；完成洗澡不自动成为完成剪毛的证据 |
| 毛型 | 服务涉及毛发处理且毛型明确；单纯剪甲不因此获得毛型处理证据 |
| 体型 | 可信、归一的体型；只转移到相同体型键 |
| 护理 | 明确相关的性格、年龄或确认的护理需求；同义的 anxious/gentle-handling 等映射为一个键 |

服务器返回可评价键，Swift 只呈现这些键；仅靠前端算候选项不是安全边界。字典、上下文、本人已完成订单、数量上限、重复键和枚举值必须共同校验。新提交同义重复或互相矛盾的键直接拒绝。没有回答的维度是未知，不是好评。

取消、未履约、未确认完成以及无可信完成记录的订单不能新增已完成服务证据。关于争议的单方报告不自动归责、扣分或封禁。未纳入协议的额外护理可保留文字反馈，不能据此产生新的结构化能力事实。

## 4. 资格与成交状态

| 结果 | 含义 | 可见性与动作 |
|---|---|---|
| `estimated_fit` | 明确范围符合，估计服务时长及缓冲能放入完整可用区间 | 正常候选；仍需美容师给出具体报价 |
| `assessment_required` | 未发现明确不符合，但非身份类必要服务细节尚未确认 | 单独分组且计数可见，报价前逐项确认 |
| `excluded` | 明确拒绝该物种/服务/体型、距离超限、无可行服务区间等 | 不作为可报价候选 |
| `pending` | 当前资格信息正在重算或无法可信读取 | 明确重试/检查状态，不伪装为无候选 |

缺身份、权限、可信地址、合法时间解释不能变成评估候选。必要细节未知也不能仅凭 15 分钟乐观下界声称完整可用；下界只用于证明不可能。

时间、资源、每日容量、提前通知、服务地点时区及 DST 继续使用[现有时间契约](../../03_backend/SERVICE_TIMING_CONTRACT.md)和现行履约资源释放规则。服务全程必须在顾客窗口内，缓冲必须落在美容师可用资源内；不把碎片时间相加，不把几条待定报价当成已占用容量。

报价前必须解决该请求需要确认的接受范围、服务能力、具体时长、价格及缓冲。未确认物种范围的旧服务需要美容师先保存范围，不能用隐式“一次报价等于全局接受”修复配置。少量负面评价不是能力不具备的证明，不自动变成资格拒绝。

范围变更沿用现有资格 revision 使旧报价重新遵守版本化同意规则；改回旧值不复活旧报价。普通排期容量变化可重试但不改写报价条款。接受时锁内重新校验明确资格、请求/报价版本、确认期限和实际资源；任何排序缓存都不能成为接受凭证。接受回执重放与当前 Booking 的读取沿用 T-388，不受新排序系统影响。

## 5. 原始评价、权重与专业适配

### 5.1 公开星级

`public_rating = sum(valid_integer_stars) / count(valid_reviews)`；仅展示时舍入。原始评价集为权威，准确整数总和和数量可以事务维护并可重建。新增、允许的撤销、删除及账号删除级联都必须更新汇总；不能只覆盖新增路径。

每个已完成 Booking 至多一份当前有效评价。不同预约可以由同一顾客评价，全部真实评价保留公开计数，界面区分评价条数与独立顾客数；内部限权不能偷偷删除公开差评。既有合法账号删除与隐私清除规则仍适用，派生证据同步失效，不能为保留评分另存已删除的个人数据副本。没有评价显示“暂无评价”，而非 3 星或 50 分。

### 5.2 一名顾客一份有时效的影响

在一次评分的固定服务器时点 `t` 上，取评价对应的可信服务时点 `t_i`，不是评价创建日期。排除未生效或未来的服务记录。半衰期 `H=180` 天是首版参数，不是实证结论。

```text
a_i = 2 ^ (-(t - t_i) / H)
A_c = sum(a_i)                     // 同一顾客、同一美容师、当前统计范围
s_c = max(a_i)
w_i = s_c * a_i / A_c             // A_c > 0；空集合贡献为 0
```

一名顾客总权重为 `s_c <= 1`。一笔新服务和十笔新服务均不能提供十个独立顾客的影响。没有新服务时，再过 H 天，该顾客总影响减半；不会被归一化重新补回 1。重复服务可以更新这一名顾客的反馈倾向，但不扩大其最大票数。

专业范围为同美容师、同物种、同固定服务、与目标请求存在有效相关回答的记录；整体体验范围为该美容师的全部有效星级记录。两种统计分别分组，不共享一个不明口径的“有效样本数”。没有结构化回答的订单不进入专业正负反馈分母；对某目标完全无关的回答也不稀释相关证据。

### 5.3 相关维度与缺失值

目标请求生成适用维度集合 G：服务、毛型、体型、护理，最多四组；不存在的需求不凭空增加维度。规范键必须完全匹配，禁止跨物种、跨固定服务或从自由文本猜测相似。

每组权重为 `1/|G|`。组内有多个适用护理键时平分该组权重。每条已完成预约对目标相关键的正、负回答分别求和，得到 `p_i` 和 `n_i`，满足 `0 <= p_i+n_i <= 1`。目标适用但没有回答的键贡献 0，不能重新分配给已填写的好评；同义键只占一份权重。

这能避免一条毛型好评被包装成全部护理能力，也防止同一订单的三个相似标签变成三次独立成功。维度自身的正负、未知与覆盖情况必须保留显示，综合分不能抹掉与当前需求相关的负面反馈。不同请求的维度集合不同，因此 F 只用于当前上下文，不能发布为美容师跨所有服务的统一能力分。

```text
P = sum(w_i * p_i)
N = sum(w_i * n_i)
F = 50 + 50 * (P - N) / (P + N + 5)
```

无相关评价 F=50；完整覆盖的五名等权好评 F=75；完整覆盖的 51 好评/50 差评 F 约为 50.47。5 是首版平滑强度。公式不是成功概率，P+N 也不是公开的顾客人数。已完成次数、独立顾客数、覆盖和最近服务日期用事实口径分别展示，不再用单一 high/medium/low 标签代表质量。

`custom_request` 不构成可复用的同类专业服务：首版 F=50，不因另一自定义服务的好评加分。已验证整体体验 Q 仍可使用；允许顾客阅读原始反馈，不编造专业等价关系。将来确有稳定子类型再单独采纳分类，不在本次增加 NLP 或无限服务目录。

### 5.4 整体体验与距离

```text
x_i = (stars_i - 1) / 4
Q = 100 * (2.5 + sum(w_i * x_i)) / (5 + sum(w_i))
D = 100 / (1 + d / 5)
```

Q 的缺失中性值为 50，与公开星级完全分开；相同预约的专业反馈和星级不是统计独立试验，组合权重只是一种产品排序取舍。Q 不能推导任何物种或护理资格。

d 继续使用服务器私有坐标计算的服务相关距离，单位英里。距离缺失属于定位资格问题，不能伪造 0 英里。匹配半径决定准入但不进入 D 的分母，美容师扩大半径不增加同一地点的 D。固定出行缓冲继续由美容师确认，D 不冒称路程、交通时间或相邻预约路线优化。

## 6. 双端排序、偏好与分页

| 页面 | 默认排序 | 显式排序 |
|---|---|---|
| 美容师待报价需求 | 预计可服务/需评估分组；各组 `B=0.70F+0.30D` | 适配、距离、最新；已有报价仍归现有 Offers 视图 |
| 顾客收到的报价 | 当前可选择报价优先；组内 `S=0.60F+0.25Q+0.15D` | 综合、距离、较早时间、价格；其他状态单独呈现 |

显式排序在相应资格组内使用真实字段：距离升序、报价服务开始瞬间升序、同币种完整报价金额升序、请求发布时间降序。当前不增加预算、动态价格、自动择日或路线偏好；不把报价前的目录价格当成顾客最终价格。同一请求的不同币种报价不能做数值裸比较，须延续现有支持币种约束。

只有默认综合/适配排序使用 2 分分桶：`bucket=floor(score/2)`，先按桶降序，再按服务器稳定 HMAC 键打破平局。不是非传递的“两者差小于 2 就视为相等”比较器。显式排序的真实主字段不能被分桶或轮换覆盖；主字段相同再按默认桶及稳定键排序。

HMAC 输入为账号、角色、查询范围、排序版本和稳定候选 ID；不因反复刷新、修改作品或同一请求重报报价而重新抽签。它不是新人曝光保证。所有合法候选仍可分页查看，不用排名阈值截断分发；保留主动 dismissal 的原请求范围，不把它学习成永久类型偏好。

首版排序模式保留在账号/角色/页面范围的本地偏好中，退出清理受保护列表；不隐式同步为跨设备硬服务政策。跨设备偏好同步不是本次前置条件。浏览、忽略、退出页面、未回复、一次取消不进入专业评分或长期偏好模型；不得建立顾客价值分、外貌分或推测支付能力。

### 全量排序先于分页

现有按时间取一页、客户端再排序的读取方式不能直接复用为“全局推荐”。新读取边界必须在服务器内完成授权筛选、资格分组、排序，然后返回页；对所有候选可发现性的承诺不能用当前页的单元测试证明。

首版选择**无持久浏览快照的版本化游标**，避免为列表建立庞大的会话存储。首屏一次一致性读取返回 `ranking_revision`、固定 `score_as_of`、排序版本、模式及游标；后续页沿用这些参数。所有可改变成员/顺序的事实必须推进该查询范围的 revision，包括软证据、请求/报价状态和资格刷新。

后续页发现 revision 不同或时间有效期已到，返回类型化 `list_changed`，不混合两次排序。客户端保留已加载内容及顺序，显示可刷新状态，停止继续拼页；不无限自动重试。明确失效的报价即时禁用。用户刷新建立新 revision；成员变化时不能承诺整个浏览会话完全冻结。

这是 R5 对初稿稳定性承诺的修正。需要测量频繁变更下的翻页重启率；若确实阻断正常浏览，再比较短期私有排序快照，而非现在先建立另一套列表状态系统。快照过期、缺数据或过载都必须显式失败，不能静默少返回后声称候选全集已结束。

## 7. 更新、过期与失败处理

| 变化 | 必须处理 | 不应处理 |
|---|---|---|
| 服务接受范围、地址、时间语义或排期资源 | 受影响资格与报价有效性，必要的 ranking revision | 不改写历史协议 |
| 新/撤销结构化评价、有效证据上下文变化 | 同美容师相关物种/服务的 F 及其解释 | 不重算无关美容师或所有时间区间 |
| 新/删除星级评价、账号删除级联 | 准确公开汇总、Q、相关顾客报价排序 | 不把重复顾客公开评价删掉以实现内部限权 |
| 技能与作品标签 | 来源明确的展示解释 | 既然不加分，就不重算专业分或禁用报价 |
| 时间流逝 | 资格有效期、报价截止和证据衰减 | 不等到有人编辑 Profile 才刷新 |

复用现有刷新队列及 worker，增加必要的原因/版本区分并按请求-美容师合并工作；不另建消息总线。单条评价不能触发全量日程分析。队列事件与业务变化同事务提交，失败事件可重试且不能吞掉，异步消费者的旧结果不得覆盖新 revision。

资格携带 `evaluated_at` 和 `valid_until`。首版缓存最长 60 秒，并在已知请求/候选时间边界更早到达时提前失效；到期进入 pending 而非继续展示确定结论。只有活跃请求进入时间到期索引和重算；未知/失败不是“零匹配”。不能仅对已有 match 设到期：因提前通知或时间区间而暂时排除的候选也需要有界的下一次评估入口，避免永远不被发现。

180 天衰减不需要每秒写库。评分固定使用读会话的服务器时点；底层可保存足够的带版本统计量或由相关索引事实计算，缓存更新时间与评分基准时间分开。准确查询成本决定是否增加窄聚合缓存，不能在缺基准时先建通用特征仓库。

软证据读取/刷新失败时保留合法的核心请求和报价，隐藏未验证的新推荐结论并提供时间排序回退；回退建立独立列表 revision，不能沿旧推荐游标拼接。未知证据不能装成“0 条差评”，暂时失败也不能装成新人。已加载旧证据须标明更新时间，接受仍只依赖权威资格与协议检查。

零候选、仅需评估候选、正在计算、网络失败必须是不同反馈。扩大距离、日期或其他顾客范围需要明确确认及新版本请求，不能由推荐系统代替顾客同意。

## 8. 架构、接口与兼容

保留 SwiftUI -> Store -> Repository -> 受控 RPC/私有 SQL 的所有权。时间与资源评估只有一个权威实现；评分不得复制它。写入核心角色校验、RLS、列权限、现有锁顺序、额度、幂等和协议检查保持原有保护。

| 边界 | 最小责任 |
|---|---|
| 服务/宠物编辑与请求发布 | 明确物种范围、结构化护理来源、版本化快照及待评估状态 |
| 评价写入 | 返回允许的上下文并验证提交，准确星级汇总，原子记录证据变化 |
| 私有专业/整体评分 | 规范化、去重、独立顾客限权、衰减、分维度解释和算法版本 |
| 匹配/报价列表仓储 | 服务端全局排序、授权范围、revision 游标和回退模式 |
| Store 与 View | 核心数据先显示，结构化状态与原因呈现，偏好选择、失效禁用和刷新 |

对外结果使用结构化原因和来源，而非从英语 `match_reason` 反向解析业务逻辑。最少携带资格状态/原因、事实与证据版本、评分基准时间、可展示的计数/覆盖/来源、当前报价评价和分页令牌。内部原始顾客 ID、精确私有坐标、未授权评价或算法秘钥不得进入解释载荷；“独立顾客数”只返回聚合计数。

后台保留精确评分组件用于调试和校准，用户界面不展示伪成功概率或平台通用美容师分数。实现可用版本化窄 RPC 替换当前列表读法，不要求拆分新的微服务或引入依赖。

后端先增加兼容契约，客户端才能读取新列/函数；旧写入若无法证明必要确认，应返回可恢复的更新/确认提示，不能悄悄放宽检查。历史已确认 Booking 保留原事实，不能为了新匹配字段破坏历史预约。

历史结构化证据从可信原始预约、协议、评价重新核对并生成可重建的使用资格，不直接覆写或删除原始评价。未知物种/时点、非法上下文、错误文本派生或冲突别名分别记录原因；不能假定所有旧 evidence 已验证。合法星级与非法结构化能力可以分开保留。修复原始缺陷与开启新推荐排序可独立发布，回退排序绝不能重新打开伪造评价入口或恢复错误均分。

## 9. 验收设计与质量边界

以下是正式实施计划必须覆盖的验收条件，不是已执行结果；沿用现有测试体系，禁止为本规格另建通用工具平台。

| 组 | 必须验证的反例与预期 |
|---|---|
| 来源 | 小型剪甲提交 Giant/无关毛型标签拒绝；猫狗证据不串用；重复别名不多计；完成但未评价不产生好评 |
| 历史 | 改宠物、延迟写评价、延迟确认完成不改旧上下文；未知时点不使用设备时间；旧错标签隔离而非删原评论 |
| 星级 | 相同星级集合任意顺序均为同一均分；800 个 5 星与 200 个 1 星均为 4.20；删除/级联/重试/并发无漂移 |
| 独立性 | 同一顾客 10 次不等于 10 个顾客；无新服务再过半衰期影响减半；晚写旧评价不重新获得满权重 |
| 部分回答 | 只有一个维度好评不被当成全覆盖；未知不是负面；负面维度仍可见；自报/作品不变成独立证据 |
| 稀疏 | 新美容师 F/Q 中性且可获得候选；custom_request 不跨不同服务共用 F；无数据与网络失败展示不同 |
| 准入 | 物种/体型/服务/坐标明确不符不进入可报价池；未知配置诚实评估；高分不能覆盖硬排除 |
| 时间 | 连续区间、碎片、跨午夜、DST、缓冲、通知天数、占用释放、同宠多单与并发仍遵守现有契约 |
| 排序 | 当前第一页之外的高分候选可进入全局前页；同分传递稳定；显式价格/时间主排序不被分桶覆盖 |
| 翻页 | 新报价/评论/状态/时间变化推进 revision；无跨版本拼页；失败保留已有列表；非参与者令牌拒绝 |
| 刷新 | 相关评论更新已有匹配；作品变化不跑时间重算；软失败不阻断合法成交；暂时未匹配的到期候选不会漏扫 |
| 恢复 | 无候选/待评估/pending/失败区分；扩大范围必须同意；取消/dismissal 不复活；回执恢复不被评分阻断 |

算法纯函数需要有界性、置换一致性、计分单调性、半衰期、别名去重和贡献总量测试。固定历史输入重放能验证结果正确，不能验证真实成交提升。快照构建、权限、事务、并发与旧客户端兼容需要数据库/仓储验收；排序、评估补齐、失效及跨页操作需要 Simulator 行为验收。真机、签名、应用商店与 APNs 不属于本范围。

排序质量先在同一合法候选集上影子计算，对比有效报价覆盖、冷启动、相关负面提示与显式偏好一致性；不能只比较均分或挑选成功样本。真实上线后按物种、固定/自定义服务、地区/服务方式及证据稀疏程度观察首份有效报价等待时间、有效报价率、确认后完成率、资格复核拒绝原因与同条件曝光。无样本报无样本，曝光本身也影响选择，不能把观察到的接单率直接当能力因果指标。

性能在实现前固定代表数据与基准，分别测匹配分发、相关证据查询、首屏、翻页重启率和队列延迟；延续已采用的容量/耗时约束，若新行为需要更改预算须写明取舍。既有测试通过和数学反例通过都不能替代线上质量或性能证据。

## 10. 可修订机制与交付边界

不可因优化而降低：权限与事实真实性、顾客明确范围、事务容量保护、原始评价保留、合法候选可发现、真实状态和公开星级准确性。

可随反例/基准调整：180 天、平滑强度 5、距离尺度 5 英里、双端权重、分桶大小、60 秒缓存上界、聚合缓存及游标实现。修改必须说明具体反例或测量、收益与代价，更新算法版本及受影响验收；不能用“更智能”作为证据。

继续检查的方式是每个核心决策都有反例和验收，不新增周期性审查规则、模型记忆文件或无限优化任务。相同目标内的更低复杂度修正自主处理；改变用户权限、公开信誉含义、自动放宽范围或新增外部依赖/远程写入，需明确新的决策/授权，不能悄悄并入。
