## 2. 目标契约

### 2.1 连续执行与停止

以下文本作为新规则的语义基准；不要求检查器逐字匹配：

> 在用户已采纳的目标及授权范围内连续完成工作。小步骤完成后继续下一步；只有目标完成、用户暂停、不可替代的信息/授权缺失或无法安全自行解决的阻塞才停止。保持改动和提交可审查，但不把一个任务编号绑定到一次会话。
>
> 普通实现选择自主判断。文档与代码冲突时先通过最小相关证据核实，不把所有漂移都当成用户决策。涉及业务规则、权限或数据真实性的未决冲突，不能用“以代码为准”掩盖。
>
> 不再按任务编号差或每周周期强制新建复查任务，不因提醒逾期阻断功能收尾。根据实际重复故障、规则冲突或用户要求触发复查。
>
> 不按固定失败次数停止。每次重试须有新的诊断或有效修正；对相同失败、无新证据的重试停止并说明阻塞。认证失败、破坏性操作和远程权限仍遵循专门安全边界。

用户授权必须继续尊重系统/宿主权限。仓库规则不能覆盖宿主强制技能；减少仓库自己设置的重复确认，不修改第三方 SKILL 缓存作为绕过办法。只读问答不分配任务编号、不写记忆、不执行收尾流程。

### 2.2 单一动态状态

保留现有 `docs/00_memory/CURRENT_STATE.md` 路径，成为唯一人工维护的动态任务事实。使用一个 JSON 代码块保存需解析的字段，避免校验自然语言句型。稳定产品事实不放这里，分支/工作区真相以 Git 为准。

目标格式示例，实施时按实际状态填写，不复制示例为完成证据：

```json
{
  "next_task_id": "T-387",
  "task": {
    "id": "T-386",
    "status": "planned",
    "goal": "精简仓库规则、动态记忆与治理检查",
    "plan": "docs/superpowers/plans/2026-09-10-lean-governance-plan.md",
    "next_action": "等待用户采纳执行"
  },
  "pending_tasks": [],
  "last_completed": { "id": "T-385" }
}
```

- `task` 可为 null；状态限定 planned/active/paused/blocked。`plan` 可为 null，小任务不强制新建计划。任务仍进行时追加的计划约束留在该计划，不复制成多份进度报告。
- `pending_tasks` 只保留非当前、已分配但未完成的任务，沿用 task 的记录形状，状态限 planned/paused/blocked；不得与当前任务或彼此重复 ID。切换前将原 active 任务置为 paused，其他状态保持真实，保存下一步和恢复必需指针；恢复时将原记录移回 task 并按实际条件设置状态，不重新编号、跳过阻塞或自动启动其他任务。只读插问不触发切换。
- `authorization`、`blockers`、`verification`、`preserve` 是各任务记录内按需填写的字段，无内容可省略；切换时随所属任务保留，不把上一任务的授权、阻塞或验证误用于新任务。已有计划/证据能承载的内容仅保留指针，无独立计划时保留最短恢复事实。
- 任务验收完成后更新 `last_completed.id` 并移除其未完成记录；不在此累加完成历史。状态和验收摘要不保存本次完成提交自己的 hash：提交结果从 Git 按任务 ID 查询，例如 `git log --format='%h %s' --grep='^T-386:'`，查不到时如实说明尚未提交；不为补 hash 再提交一次。既有验证基线的提交号仍可引用。
- `next_task_id` 只在本文件递增，不从旧账本/归档编号差推导治理周期；禁止复用已分配 ID。同一 checkout 不并发写状态，不为此新建锁服务。
- `authorization` 记录用户已给出的具体范围和限制，不表示文件本身能授予权限，也不因任务切换扩大权限；不得记录密钥。`preserve` 只记录恢复必需的未提交工作边界，不复制完整 diff。
- 每项 `verification` 使用 `scope`、`command`、`basis`、`result`、`evidence`；basis 说明相关提交/未提交变更与环境。代码、配置或相关环境变化时复核对应证据，不机械重验其他领域。
- `WORKLOG`、`TASK_LEDGER` 退出日常写入。历史用现存记录、Git 和必要的验收文件追溯；小改动不再强制新建验收报告。
- 短问答只查所需来源；实现先看 Git 和当前状态，再直达代码；只有复杂目标才读当前计划。中断恢复不重建聊天/归档链，也不强制人工 `/compact`。

### 2.3 验证与安全

| 变更 | 必要验证 | 不作为默认前置 |
|---|---|---|
| 只读问题/讨论 | 核实被问到的事实 | 编号、记忆写入、构建、hygiene |
| 文档/规则 | 相关链接、状态语义；改检查器时运行其行为测试 | iOS、Simulator、Supabase |
| 局部客户端修改 | 有效针对性测试；编译性改变需构建，交互变化需合适运行验证 | 无关模块全量回归、另建通用测试平台 |
| 共享业务或集成节点 | 对应集成/完整回归及必要运行证据 | 无变化后的重复完整回归 |
| 数据库/权限变更 | 当前受影响定义、授权、并发/负例/回滚与数据恢复 | 从本治理计划推导任何远程授权 |

保留：用户改动保护、最小权限、凭据不入日志/客户端、已应用迁移不可改写、重要业务不变量、授权测试数据恢复、真实报告失败与跳过项。Xcode 单写者和 linked CLI 顺序执行等已知工具约束不因追求并行而取消。Git 提交/推送只沿用现有已验证完成任务授权，不扩展为 checkpoint、强推、PR 或合并授权。

## 6. 成效判定与回滚

结构验收目标：规则入口不再串读五份流程；动态任务事实只维护一处；普通任务不强制追加 Worklog/验收报告；保留检查器默认摘要不超过约十行（多项真实错误除外）。这些是目标，不增加新的行数/字数硬阻断测试。

执行前后记录相同定义的入口字节数、动态状态写入文件数、工具调用/返回量、无关停止次数和必要验证次数。实际降本/加速在随后自然发生的问答、局部修复、共享修改中观察；尽可能保持模型/推理档位/环境一致，无法控制缓存或任务差异时说明限制。不为了测速度制造业务变更，也不将后续任务变成本治理的无限完成前置。

如果关键安全边界、未提交原文或恢复能力损失，停止有风险的后续操作并对本任务文件做定向修复/恢复；不得回退已完成的功能可靠性实现。新规则与新检查器是同一恢复单元，不能只恢复其中一半。已推送后的纠正用新的前向提交，不强推历史。

执行结果只需在此补充：完成/未完成包、关键决定、必要验收命令/证据、遗留限制。实际完成提交号从 Git 查询并在完成回复提供，不回写自身 hash。**不把治理计划的保存说成治理已经实施，也不把取消旧周期规则说成历史检查从未失败。**
