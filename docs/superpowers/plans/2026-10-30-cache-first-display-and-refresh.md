# T-428 缓存优先显示与后台刷新修复计划

日期：2026-10-30。范围：正式 App 的顾客端、共享页面和已发现问题的美容师端页面。本轮交付为计划；下列实现和验收尚未执行。

目标：已有内容立即可见，刷新在原页面内完成；同一账号重启 App 后能先浏览本地快照。缓存不得伪造最新业务状态、恢复失效登录或绕过访问权限。视觉检查由用户完成。

依据：当前代码审查、用户本轮要求及 [现有加载与导航规范](../../01_product/LIVELY_UI_SPEC.md)。执行遵循 [Development Guide](../../05_workflow/DEVELOPMENT_GUIDE.md)，单线程推进，不另建工作台、同步框架或多份过程报告。

## 1. 修复边界与现状

现有 Store 已有相当多的内存保留、请求取消、generation/revision 和写后防旧读覆盖机制，应直接复用。账号展示快照、宠物照片、图片文件缓存、聊天已读时间也已存在，但它们不等于请求、预约或聊天正文的重启缓存。

| 问题 | 修复方向 |
|---|---|
| 聊天入口先等待预约/会话解析，缓存正文仍不可见 | 已验证过的会话映射与正文先展示，后台核验与订阅合并；无缓存才等待首批消息 |
| 美容师档案入口清空 current/profile，每次新建 Store，重试照片也重载全文 | 保留候选摘要与完整档案；会话内复用已有档案 Store；照片单独重试 |
| 收藏列表被“可发送请求列表是否加载”连带遮住 | 浏览独立就绪，发送操作独立核验 |
| Grooming 等请求和预约两路都完成才显示 | 已知内容先显示；缺失部分单独等待，不提前宣称全部为空 |
| 美容师 Home 刷新清空计数；请求详情等待授权时完全空白 | 保留上次计数及安全摘要，明确其尚在更新；权限相关内容仍等待核验 |
| 日程只保留一个日期范围 | 有界保存已看日期；原本同一范围刷新已保留日程，沿用该行为 |
| 成功读到空列表，下一次刷新又被当成第一次加载 | 明确“未知、已知为空、已有内容”，与 refreshing/error 分开 |
| 返回标签页会把已显示内容重新隐藏并播放入场 | 普通返回保留内容与滚动；首入场、显式 Preview Replay、后台暂停分别处理 |
| 重启缺少业务快照，且账号角色入口还会等待远程 profile | 补轻量本地读快照，并打通登录会话恢复后的缓存页面入口 |

不包含：离线发送/报价/接单队列、数据库迁移、匹配算法调整、新登录机制、页面重新设计、远程部署、真机或签名工作。已有未完成操作恢复机制继续独立负责写入恢复。

## 2. 统一行为契约

### 2.1 内容与刷新各自管理

- 内容是否可展示，由已有数据或成功空结果决定；`isLoading` 仅描述正在读取。不能再用 `isLoading && items.isEmpty` 同时推断初次加载和刷新。
- 优先顺序：当前 Store 内存 → 同账号、同角色、同查询范围的有效本地快照 → 云端刷新。已有内存直接渲染；异步磁盘恢复不得覆盖更新的内存、编辑草稿或网络结果。
- 有内容时不清数组、不卸载正文、不显示全页骨架、不重置滚动和选择。沿用页内轻量更新提示；聊天只用名字下方状态。刷新失败保留内容，提示“暂未更新”及重试。
- 从未取得数据才使用该页面现有首载占位；聊天不重新加入骨架。已知空结果可立即展示，并注明刷新状态；分页快照不完整时不能宣称“没有更多”或“没有待办”。
- 各模块独立就绪：头像、照片、次要元数据、发送资格、另一列表的延迟不能遮住已经可读的内容。
- 首次激活 Store 和每次进程重启恢复快照后刷新一次；普通返回只在距离最后成功核验超过 60 秒、明确失效或上次失败时刷新。手动刷新和相关业务事件不受 60 秒限制。同一作用域合并重复在途请求，不另加轮询器；实时订阅继续复用。60 秒仅适用于普通展示刷新，不能抑制原有授权、接单/报价有效性和写前核验。
- 数据与入口仍使用现有稳定 ID。刷新保留已有行的身份；非必要不对整个列表增删播放动画。缓存内容到最新内容只作必要的局部变化。

### 2.2 本地缓存最小实现

在 `Core/Infrastructure/LocalReadSnapshotCache.swift` 新增一个可注入的文件读快照适配器，沿用 `LocalProfileSnapshotCache.swift` 的目录、编码和原子写入做法，但新文件的读写、编码与清理由独立 actor/串行执行器完成，不在 MainActor 上处理。已有照片、图片和已读缓存继续使用，不迁移重写。

接口只需异步 read/write/remove、按账号清理和内存/临时目录替身；不建立通用 Store、事件总线、后台任务调度或数据库。各 Store 决定何时恢复、刷新和失效，业务 Repository 继续负责真实读写。

| 契约 | 默认规则 |
|---|---|
| 键 | 环境命名空间、账号 ID、角色、资源种类、查询范围；详情含实体 ID，报价含 request ID，日程含起止时间及业务时区 |
| 包装 | schemaVersion、savedAt、payload、覆盖范围/是否完整。缺省、版本不兼容、损坏或超期均为未命中，正常走远程读取 |
| 数据 | 只保存成功确认的展示字段；现有模型适合时复用 Codable，否则加少量领域快照类型。不得为序列化整个 Store 而改业务模型 |
| 有效期 | 初始最大保留 7 天；这不是业务有效期或 7 天免刷新。重启必刷；超过保留期不再用于展示 |
| 数量 | 普通列表每作用域最多 100 条；最近 20 个会话、每会话最近 50 条消息；最近 20 个美容师档案、7 个日程范围。截断必须记录为部分覆盖 |
| 容量 | 每账号读快照合计最多 10 MiB，不含现有图片缓存；写入时淘汰最旧快照，单条异常过大则跳过缓存。常量集中定义，不另做调参工具 |
| 文件 | App 私有目录、原子替换、文件保护、排除备份；落盘失败不影响网络成功结果。未发送草稿、凭据、签名 URL、授权结论和分页游标不落入此缓存 |
| 安全退出 | 退出成功、会话确认失效、切换账号、删除账号时停用旧命名空间并清理新读快照；晚到读写不能重新创建它。退出失败按实际登录状态处理，不能假称已退出 |

只有仍有效的 Store/session generation 可以应用和保存快照；缓存写入及退出清理在同一串行边界检查会话代次，防止“退出清理完后旧请求又落盘”。快照时间使用真实取数时间，恢复、失败重试或单纯重新保存不能续期陈旧记录。

对数据集的成功更新应替换对应范围；确认删除/失去访问权应删除对应实体及引用。已有 mutation revision 防护同时覆盖内存和落盘；有疑义时删除该范围快照，不能让重启恢复旧状态。删除与撤权依据现有 Repository 的明确结果；超时、网络错误及无法分类的失败不能冒充删除或权限撤销。不同成功时间的模块分别保存；刷新一部分不能把未刷新的旧字段、旧分页一并标成刚取得。

### 2.3 恢复范围与业务可靠性

| 数据 | 重启后先展示 | 仍需最新核验 |
|---|---|---|
| 自己的账号、宠物、请求、预约、通知、报价、收藏 | 最后成功确认的列表/详情展示字段与成功空结果 | 提交、取消、改期、接受报价、发送邀请等沿用现有服务端前置条件与冲突处理 |
| 聊天 | 本账号此前确认的会话、关联映射和消息；UI 标明刷新状态 | 当前会话参与权、新消息读取与发送；缓存映射不是授权凭证 |
| 美容师公开档案 | 之前成功取得的展示字段、列表带入的摘要 | 当前可见性、可邀请/匹配资格；图片仍遵守已有访问策略 |
| 美容师待接请求 | 已授权读取过的最小卡片摘要，字段不超过原列表允许展示的内容 | 精确地址、联系方式、私有照片、完整授权详情和报价资格；这些不新增磁盘缓存 |
| 日程、首页统计 | 对应日期范围的日程摘要、上次计数 | 范围完整性、实际空闲、接单/改期冲突；部分结果不能推导可预约时段 |

对于自己的详情也只存页面需要的最小字段；不把其他参与者的敏感字段整体编码进快照。受保护照片继续使用 `PrivateImageLoader` 的 `authorizationRequired`，不能为提速改成普通缓存策略。

重启入口仅在现有 Auth Repository 已恢复**同账号且未过期**的会话时，使用该账号上次服务端确认的 MarketplaceProfile（ID、角色、展示名）先建立原有页面树，同时刷新 profile。该快照只能决定展示哪个已有标签页，不能产生 AuthSession 或赋予权限。角色核验期间允许浏览快照，依赖已确认身份/角色的业务写入等待核验；不靠禁用整个页面阻止操作。profile 返回同角色时保留 Store 和导航身份；确认不存在/角色变化/会话失效时撤销旧范围并按真实结果路由。临时断网保留只读内容和重试；无合法会话或无可用档案快照时沿用现有入口。

## 4. 最小但足够的验收

验证重点是时序、身份和数据一致性，不是测试数量。优先扩展既有 fake repository、可控 continuation 和临时目录；不新建大型测试工具，不依赖真实网络或 sleep 模拟等待。

| 场景 | 必须证明 |
|---|---|
| 内存返回、磁盘重启、有缓存刷新 | 云端未返回时内容已可见；保留内容身份和选择 |
| 成功空结果、部分列表、一个模块失败 | 区分已知空/未知/部分；其他模块照常可读 |
| 更新失败与恢复 | 保留旧内容和真实错误提示；成功后就地更新 |
| 慢磁盘、迟到网络、并行刷新、成功编辑 | 旧读不能覆盖新值或草稿；同范围请求合并 |
| 新建/修改/删除后重启 | 不恢复旧状态；未确认写入不被误当成功 |
| 退出/切换账号/删除账号、过期登录 | 不串数据；旧异步回调无法重新落盘；缓存不能恢复登录 |
| 档案入口恢复、角色校验失败/改变 | 有效会话可先读缓存；权限由最新结果决定；无 Store 重建闪屏 |
| 聊天实时事件与初始快照交叉 | 消息不重复、不丢失；可见前不误标已读；原授权链仍在 |
| 请求撤权、图片授权、候选请求 revision | 删除相应受保护内容；缓存不扩大访问或操作资格 |
| 日程时区/日期切换与分页 | 不串日期；部分缓存不被当成完整空闲证明 |
| 缓存超期/损坏/过大/写失败 | 自动回退，不崩溃、不影响成功业务结果 |

日常仅运行当前工作包新增/受影响用例，使用现有 Xcode 测试目标的 `-only-testing` 或现有工具筛选能力，不为筛选修改项目测试脚本。最终因涉及共享 Store/DesignSystem，串行执行一次 `./scripts/ios-build.sh`、一次 `./scripts/ios-test.sh` 及一次 `./scripts/preflight.sh`；文档运行 `node scripts/context-hygiene-check.mjs --full` 和 `git diff --check`。本轮仅编写计划，**不执行这些构建或应用测试**。

最终运行态证据限定为一条使用现有隔离 fixture 的冷启动恢复路径：预置快照 → 结束并重启 Simulator App → 延迟后台结果时确认缓存可用 → 释放刷新。无需新建测试账号、注入云端或反复逐页点击；其余边界由针对性 Store/缓存测试覆盖。只有新增修改或明确失败才重跑相关范围，不因观察到普通工具噪声扩大回归。

用户视觉检查：返回 Home/Grooming 不再整体闪空；Grooming → Message 旧消息立即可见、Updating 结束自然；收藏/档案刷新不消失；重启仍见已有内容；日程切回已看日期不整页等待。由用户反馈实际视觉问题后定向处理，未检查时不能宣称视觉已通过。

## 5. 完成标准与自检

完成实现需同时满足：上述页面范围接入、重启入口贯通、权限与失效规则成立、必要逻辑/集成验收通过；仅缓存工具完成或局部测试通过均不算完成。视觉验收单独标识为用户负责，技术完成不冒充用户已确认。

计划自检结论：已覆盖原审查的显示门槛、入场动画、已知空结果、权限详情、日程范围与重启持久化；另补上重启时云端 profile 的串行门槛。只新增一个轻量文件快照适配器及必要领域快照，复用原 Store、Repository、会话保护和测试。明确限制缓存数量/时间及字段，未增加离线写入、后台轮询、远程变更或视觉自动验收前置条件。
