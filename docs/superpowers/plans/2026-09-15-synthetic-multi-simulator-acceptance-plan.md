- “无错误运转”指本计划全部必测场景符合冻结预期、已知阻断缺陷清零、无未解释失败，不是保证软件永远零 bug。正确拒绝冲突、过期或越权属于通过，不要求每次提交都成功。

### 2.2 实际坐标、时间和规模

- 使用既有测试地址能力为每个地址记录确定坐标和来源；无真实地址时保留“合成位置”标签。用 PostGIS 距离计算预期，不拿社区中心点距离冒充路线距离；同社区候选安排不同的固定偏移点，另保留一个真正同坐标并列案例。
- 执行前一次冻结 `anchor` 和日期映射。普通服务日整体后移整数周，保留星期、持续时间和所有重叠/相邻关系。金额单位为 cents，USD；精确体重按当前体型档位准入，不假设系统存在精确设备承重模型。
- R23 自然到期另设运行时窗口：使 A 的 `proposed_start - 5 minutes` 先到、B/C 的服务时间更晚，需求本身尚未到期。若发布 UI 无法表达这个窄窗口，可预置一个通过正常发布 RPC 创建的边界需求，明确记为 setup，不能冒充 UI 发布；A/B/C 报价、B 撤回和顾客确认页操作仍走 UI。不得用撤回 A 替代 A 到期，不改系统时钟或已发布条款。
- L05 使用独立的当天可开始服务场景，实际经过 UI 开始、完成与评价；历史导入不替代此用例。按现有履约时间门禁排任务，不通过改服务器时钟、关闭校验或修改在测预约终态加速。
- 客户端默认页长为 25，见 `Core/Models/MatchRanking.swift`。建立一组美容师可见的 **26 个合法需求**及一组顾客收到的 **26 个有效报价**，两端均须真实出现第二页。使用 12 个主美容师加最多 14 个既有备用美容师，禁止由同美容师重复报价凑 26。规模辅助需求/报价可用受控 RPC 预置，但不算 UI 发布/报价通过次数。
- 规模阶段使用独立备用 viewer，或在主场景验收并清理后建立规模池；核验的是该账号完整授权列表恰好 26 项，不通过按 run ID 在 UI 中过滤掉其他候选来凑数。若存在非本次归属的活动需求/报价/会话，不删除它们，改用空闲账号或先解决隔离条件。
- 压力、并发与破坏性分支使用带父场景 ID 的独立副本，避免一个成交消耗后续比较的候选。24/57 是来源场景数，历史 1,228、规模辅助、重试与分支副本分别计数，不宣称只产生了 24 个远程对象。
- V-05 冷启动变体复用一个未导入评价的备用美容师，采用 G05 的合法服务/位置条件及 R03/R20/R22 的关联副本；不删除主 G05 的已导入历史。固定该变体的账号和业务 ID 后验证同桶稳定性，不能要求换了 HMAC 输入仍复现旧 run 的逐项顺序。

### 2.3 注入和恢复协议

先记录别名 -> seed ID -> Auth UUID -> 角色，不以排序中的“第几个账号”临时决定。资源索引声明有 50+50 个资料，但不证明远端可用；执行时只核验选中的既有身份、角色、登录及空闲状态。主样本不与真人活动、未完成预约或其他未恢复 run 共用账号；发生冲突换同池空闲身份并冻结映射，不重置账号。

预检还须覆盖目标美容师已关联的非归属活动需求/报价，避免修改其服务范围后影响别人正在进行的交易。旧数据有评价时先评估是否能选无历史账号；不能删除既有评价或把它忽略后宣称上表就是实际总数。无法隔离时明确阻断注入，不静默覆盖。

注入前保存目标资料、服务、地址、设置、评价汇总基线、既有对象 ID 和配置指纹；产出 manifest 后才能第一笔写入。每批记录 intended IDs、operation IDs、输入哈希和回执，超时先核对该批是否提交，不盲目重复。注入应真实提交，使多台客户端能读取；不能沿用 C 的“事务末尾 rollback”作为客户端准备。

历史导入复用已有 TestOps 的受控历史方式，保留外键、RLS、触发器和上下文约束；必要的历史专用写上下文只限有授权的播种事务，不进入 App 或在测交易。不得直接填充评分、匹配结果缓存、专业投影或伪造公开统计来让页面看起来正确。正常 worker 排空后核对明细、计数、专业证据和账号范围，证明不是全体 `no_evidence`。

先用一个最小批次证明“注入 -> 两端可见 -> 清理 -> 恢复”，再装载全量基线。所有行以精确 run ID 和捕获 ID 联合归属；清理只删除当次对象，按依赖顺序处理预约、评价、通知、会话和地址，正常 worker 收敛私有投影/候选/队列。只恢复被本次修改且未被外部修改的资料字段；版本/时间戳允许合法前进，不倒退。发现第三方更新即保护该字段并报告具体恢复冲突。

并发屏障以两端确认页 ready 为起点，记录请求发出/完成区间。每类竞争做 3 组新副本，至少有一次请求区间确实重叠才算覆盖；若 UI 自动化始终只能顺序点击，标记 UI 竞争未覆盖，再改进驱动。真实认证 HTTP 同步竞争可辅助验证锁，但不能替换这项客户端结果。

## 6. 冻结断言与性能预算

所有 60 例先确定场景预期，再执行；不以现有 API 返回值本身生成“正确答案”。金额/时长/资格/占用从来源明细独立计算，F/Q/D/B/S 使用既有独立 oracle 与固定服务时点核算，分数误差 <=1e-7，计数和业务 ID 必须精确相等。对 HMAC 并列不读取或导出签名密钥来制造 oracle；验证主键/桶顺序及同账号同版本重复读取稳定，相关顺序由可见合法结果保留证据。

S04-S06 保留原 T-391 预算与节奏：静态、无关每 10 秒、相关每 60 秒、相关每 10 秒，各角色各 10 次首次浏览，共 80 次。每组五次页间 1 秒、五次 5 秒，变更相位按既有 `fixedPagingSchedule` 固定。首次完整分别必须为 **10/10、10/10、至少 9/10、至少 8/10**；所有中断在变更停止后一次刷新完成，重复/遗漏为 0。失败与恢复分母均保留。

规模本次固定为双端各 26 个合法候选。80 次可由真实角色 HTTP 以每页 6 项、5 页精确实施，明确不是 5 页 UI 证据；S01/S02 另以 App 原生 25 项验证真实第二页。S04-S07 每类每侧至少一段多模拟器客户端证据，相关/硬变化必须实际提交在首屏与下一次读取之间，不能以未遇到变更的一次浏览算覆盖。持续新评价的客户端路径与 SQL 控制更新旧评价的压力模型分别标识，后者不冒充用户编辑功能。

先定位修复 V-04，再执行受影响矩阵，不重复整套已知失败运行。不通过时仍为本地阻断，不能调慢浏览、缩小候选池、隐藏评价变化或取消硬资格校验来通过。若需要调整软证据一致性/短期快照策略，先在同一任务记录最小设计取舍、过期/隐私/容量/兼容规则，再实施和验证；不预建通用快照服务。

读取预算仍为 SQL P95 <=1500ms、真实角色 HTTP P95 <=2500ms，各侧各 30 次，首读单列。顾客从旧两报价变成 26 报价，旧性能结论不能代用；不把慢请求排除或只统计成功。UI 记录动作到状态可用的时间与错误，不把 XCTest 查找耗时伪装成网络延迟。

故障注入只作用于指定测试会话/单次请求；使用现有 DEBUG repository 机制，不改整台 Mac 网络或其他应用。必须区分“提交前失败”和“提交后丢响应”；后者需权威回执证明已提交。未真正切断网络时标记 DEBUG fault injection，不声称真实断网。
